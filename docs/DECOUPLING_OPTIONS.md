# 与 qq-bridge 脱离：路线与工作量

调研日期：2026-10-25。此文件是方案分析，**当前1.6版仍依赖 qq-bridge，未安装替代通道、未迁移真实账号，也未升级服务器 DSH**。

## 先区分三个层面

1. 情绪、关系、资料算法：多数已是独立 JavaScript，可复用。
2. 可信会话数据：群/私聊、真实发送者、消息ID、引用对象、机器人回复回执、白名单、会话绑定。
3. QQ 通道与自主参与：接消息、保持登录、发送、观察未读、唤醒、配额和失败重试。

第一层独立不代表后两层可以删除。当前 runtime.js 读取 qq-bridge 的 config.json 和 state/，主动聊天调用其本机接口；host.js 的路径解析、index.js 的会话校验也依赖它。直接去掉路径检查只能让插件“加载”，不能保留正确的关系和主动聊天。

## 可选路线

以下难度与工作量为基于当前代码的工程估计，包含适配和隔离测试，不是已经验证的工期。真实账号权限、宿主版本差异及长期稳定性测试可能增加时间；不建议承诺“改两处路径即可”。

| 路线                         | 脱离后依赖什么                                   | 保留能力与限制                                                                                                           | 难度 / 初步量级                                 |
| ---------------------------- | ------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------- |
| A．只挂普通DSH会话           | DSH本身，手动绑定会话与对象                      | 情绪/状态表达容易保留；网页单人聊天可用。缺少可信群成员元数据时，无法完整保留多人关系、群旁观与自主找群友                | 情绪试用低，约2–4开发日；不等价于完整QQ群友     |
| B．适配已有OneBot通道插件    | DSH＋例如dsh-onebot-qq＋使用者自己的OneBot登录端 | 最接近现有QQ账号群友。复用收发、连接、消息解析，但仍需真实事件和发送回执适配，不能只读取模型对话文本                     | 中等，约4–8开发日完成受限原型，完整群聊回归另计 |
| C．适配dsh-im等多平台通道    | DSH＋dsh-im及其平台账号/官方机器人               | 适合推广到多平台。必须重做带平台命名空间的身份、会话及回执；官方QQ标识是OpenID，不能假设等于原QQ号，也不能直接合并旧好感 | 中高，约6–12开发日；宿主升级兼容和平台权限另计  |
| D．QQ Life内置最小OneBot通道 | DSH＋OneBot登录端，不再依赖另一桥接插件          | 可自行设计群友参与与唤醒。代价是自己维护鉴权、重连、去重、消息队列、发送回执、图片/引用、白名单及故障恢复                | 高，约2–4开发周；媒体功能越多越久               |
| E．QQ Life直接接官方QQ机器人 | DSH＋QQ开放平台机器人应用                        | 不再使用QQ账号登录端；但接入身份、群消息范围与主动发送要按官方能力和授权验证，不承诺与普通QQ账号群友等价                 | 高，约2–4开发周；申请、平台限制和审批时间不计   |

A只要“能装上”最省事，但为了完整群友能力仍需要可信输入，不能把模型从正文猜出的名字或QQ号当真实身份。

## 已查到的实现与限制

- **DSH原生提示接入**：官方提供有作用域的提示段和 system-prompt/assemble 流水线。因此，情绪提示本身不必靠 qq-bridge 注入；难点是给它可信的对象与消息数据。[官方提示系统文档](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/core/system-prompt/README.md)
- **OneBot通道**：dsh-onebot-qq 的项目说明包含正/反向WebSocket、每QQ会话持久Agent、群消息和发送工具，并声明支持DSH 0.2.0线。这里是作者声明，不代表本插件已和它实测互通；是否能提供足够稳定的外部事件接口仍需下一轮查源码/做原型。[dsh-onebot](https://github.com/mario841859784/dsh-onebot)
- **多平台通道**：dsh-im 提供多平台会话、群消息记录及主动投递；文档公开同宿主 dshIm 服务、保存投递目标与send方法。主动投递能力不等于已经有本插件所需的逐条入站/已发回执接口，后者仍需核实。其当前README支持基线是DSH **0.2.1-rc.2 / Session v4**，高于现有服务器 **0.2.0-rc.2**，应另开兼容实验，不直接升级生产环境。[dsh-im](https://github.com/xmanrui/dsh-im)、[主动投递接口](https://github.com/xmanrui/dsh-im/blob/main/PROACTIVE_DELIVERY.md)
- **人格插件不等于通道适配器**：dsh-companion 自身也提供人格和长期记忆，并能遮蔽默认人格。它的通道服务可供研究，但整套叠加可能重复管理人格和记忆，不符合“保持原人格卡”的目标。[dsh-companion](https://github.com/yyh-001/dsh-companion)
- **直接接协议**：OneBot11标准有消息事件与群/私聊发送接口；协议解决格式，不代替登录端，也不会自动替我们做好DSH会话、关系归因和自主参与。[消息事件](https://github.com/botuniverse/onebot-11/blob/master/event/message.md)、[公开API](https://github.com/botuniverse/onebot-11/blob/master/api/public.md)

## 推荐顺序

先抽象“通道适配器”，保留当前qq-bridge适配。核心只接收统一的消息、会话和发送回执，不关心文件放在哪里。可设计的概念接口包括：订阅真实消息、订阅成功发送回执、识别当前会话/参与者、列出允许目标、检查在线能力、请求自主唤醒。

之后优先尝试路线B：现成OneBot通道最接近当前需求，QQ数字身份迁移也较直接。路线C适合扩大用户范围，但要按“平台＋账号＋用户ID”隔离资料，避免不同平台ID碰撞，不能自动把OpenID映射到真实QQ。

适配器应声明能力：如果没有发送回执，不形成长期交往；不知道真实发言人，就不按昵称猜关系；不支持主动唤醒，就隐藏主动聊天能力。这样允许不同平台有不同功能，而不是勉强假装全部支持。

只有确认现有通道无法提供必要事件、或其参与机制不适合群友模式时，才考虑路线D自己维护通道。路线E更适合明确接受官方机器人形态的人群，不能作为现有QQ账号行为的默认替代。
